# Đối chiếu Demo A (SDV/HMA) với Demo B (HMA + Random Forest chọn vị trí)

Demo A là mốc SDV/HMA; Demo B tái sử dụng nội dung HMA và dùng Random Forest để phân bổ vị trí theo rủi ro. Kết quả placement mới được trình bày riêng bên dưới. Số liệu classifier ở các phần sau là kết quả lịch sử và không đo hiệu quả vị trí. Tất cả kết quả đều thuộc mô phỏng lab, không phải triển khai sản xuất.

**Ghi chú cập nhật giao thức:** phép chạy đang được lưu bên dưới là kết quả cũ với hai mục tiêu và truy vấn 250 ID cao nhất; hit 100% ở cả A/B bị bão hòa nên không đủ để kết luận placement nào tốt hơn. Script hiện đã được nâng cấp để mặc định chạy mọi phòng ban, 20 lần lặp theo cặp, thêm lấy mẫu có seed và lọc theo ngày tuyển dụng; hai kiểu truy vấn mới là phép đo chính, còn truy vấn ID cao nhất được tách thành chẩn đoán. Chạy capture/train mới sẽ thay thế các artifacts kết quả hiện tại; các số cũ dưới đây được giữ làm lịch sử, không được trình bày như kết quả của giao thức mới.

## Phép đo chính cần dùng cho nâng cấp vị trí

So sánh dùng cùng database `employee`, 50 token mỗi demo, cùng candidate HMA, cùng mục tiêu attacker và 5 lần lặp. Mặc định mục tiêu là `d001,d002`; truy vấn mỗi mục tiêu lấy tối đa 250 nhân viên theo `emp_no` giảm dần.

### Kết quả placement hiện có

| Mục tiêu | A phiên có hit | B phiên có hit | Token records A mỗi query | Token records B mỗi query |
|---|---:|---:|---:|---:|
| d001 | 5/5 (100%) | 5/5 (100%) | 2 | 5 |
| d002 | 5/5 (100%) | 5/5 (100%) | 14 | 5 |
| Tổng | 10/10 (100%) | 10/10 (100%) | 80 lượt xuất hiện | 50 lượt xuất hiện |

Mỗi demo có 10/10 truy vấn mục tiêu trả về ít nhất một token. Vì vậy, theo chỉ số hit nhị phân, A và B bằng nhau trong lần chạy này. A tạo nhiều token records được trả về hơn (80 so với 50), do HMA đặt 14 token vào d002 trong khi B phân bổ 5 token cho mỗi mục tiêu. Đây là số bản ghi token xuất hiện trong kết quả, không phải số phiên phát hiện.

**Giới hạn quan trọng:** phép đo hit nhị phân bị bão hòa. Token IDs nằm ở dải cao, và truy vấn chọn 250 ID cao nhất; do đó mọi token trong hai phòng ban mục tiêu đều lọt vào kết quả. Kết quả hiện tại không chứng minh RF placement cải thiện xác suất hit. Với hai mục tiêu này, A đưa nhiều decoy records hơn vào kết quả; một phép thử dùng lấy mẫu/bộ lọc khác và nhiều mục tiêu cần thiết để đánh giá placement toàn diện.

The 10,000 employee IDs are read from the Bytebase `mysql/dataset_large` file and assigned to scenarios. Static token budget is modeled as 50.

## Scenario families

Per-family rates below are the mean alert rate across the five held-out repeats. For attack families, this is the detection rate; for normal families, it is the false alert rate.

| Scenario family | Label | Static hit | Random Forest |
|---|---:|---:|---:|
| Routine point lookup | Normal | 0.62% | 1.03% |
| Legitimate bulk report | Normal | 4.66% | 0.00% |
| Off-hours maintenance | Normal | 0.60% | 0.80% |
| Rapid ID enumeration | Suspicious | 21.71% | 100.00% |
| Department sweep | Suspicious | 31.45% | 100.00% |
| After-hours bulk access | Suspicious | 19.33% | 97.94% |
| Low-and-slow targeting | Suspicious | 0.57% | 17.28% |

On this synthetic benchmark, Random Forest risk scoring improves recall by 61.47 percentage points and F1 by 0.579 over the static hit rule. Its FPR is 1.40 percentage points lower here. Combining model risk with token hits slightly increases recall but also raises FPR. These are simulation results, not evidence that ML will outperform Static on real database traffic.

## Protocol and limits

- Positive label: a generated suspicious behavior scenario. Seven families are included: routine point lookup, legitimate bulk report, off-hours maintenance, rapid ID enumeration, department sweep, after-hours bulk access, and low-and-slow targeting. All methods use the same held-out rows.
- Demo B features: returned row count, access hour, number of tables, recent query frequency, query duration, and department-query indicator. The generated distributions include overlapping normal and suspicious cases.
- Demo B models are trained only on each run's training partition and scored on its held-out partition. The saved gateway model is separately trained on seeded synthetic scenarios for the interactive prototype.
- Employee IDs come from the public dataset, but scenario features, labels, and token hits are generated. The benchmark does not query MySQL or replay real Gateway logs; it compares methods on the same reproducible synthetic rows and does not establish real-world detection efficacy.
- Latency is in-process model prediction time on this machine and excludes MySQL, process startup, network, and alert-writing costs. Compare it only as a rough model inference cost.
- Adaptive placement is a separate prototype that redistributes the same 50 tokens based on department risk observations. Its update cost must be measured on a configured MySQL instance; it is not inferred from this synthetic classification benchmark.

## Reproduce

From `RandomForest/`, after preparing the dataset and installing `requirements.txt`:

```powershell
.\.venv\Scripts\python.exe evaluation\run_common_scenarios.py
```

The command writes detailed held-out predictions to `results/ab_query_results.csv`, aggregate results to `results/ab_metrics.csv`, per-family results to `results/ab_scenario_metrics.csv`, and protocol/results to `results/ab_metrics.json`, and the prototype model to `models/random_forest_synthetic.joblib`. The Streamlit dashboard displays aggregate and per-family comparison tables after the CSVs are generated.

## Controlled live MySQL query simulation (2026-10-26)

The archived 2026-10-26 classifier run executed eight scripted query-session families against the shared `employee` database. It produced 40 sessions and 980 SELECTs per demo. Its results are historical detector metrics; they do not measure the new attacker-objective placement scenarios. Demo B features came from MySQL, while labels came from the scenario script.

### Session-level comparison

| Detector | Sessions | TP | TN | FP | FN | Accuracy | Precision | Recall | F1 | False positive rate |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Demo A static token hit | 40 | 10 | 15 | 0 | 15 | 62.5% | 100.0% | 40.0% | 0.571 | 0.0% |
| Demo B live Random Forest (calibrated) | 40 | 25 | 15 | 0 | 0 | 100.0% | 100.0% | 100.0% | 1.000 | 0.0% |
| Demo B Random Forest OR token hit | 40 | 25 | 15 | 0 | 0 | 100.0% | 100.0% | 100.0% | 1.000 | 0.0% |

This calibrated run had no false alerts among 15 benign sessions and detected all 25 scripted attack-like sessions. The threshold target was FPR <= 10%; the selected threshold was 0.9865. This is a small, repeated, scripted lab set with the same eight scenario families represented across repeats. The result must not be presented as production performance or generalization to unseen behavior.

The scenario-family holdout is stricter than a random query split, but all data still comes from scripted scenario templates run against a single local dataset. The hour feature records the actual host hour; this run does not establish off-hours performance or generalization to new users, databases, or real incidents.
